A Qonstruct model becomes executable through a transformation process that translates the visual model into an executable representation. Depending on the elements used in the model, this representation is either a **quantum circuit** or a **quantum workflow**.
The transformation is performed by the [quantum low-code backend](https://github.com/LEQO-Framework/leqo-backend).

## From model to execution

The transformation starts with the Qonstruct model and analyses its structure, nodes, groups, connections, and metadata.

There are two main execution paths:

* A model containing only executable quantum operations can be transformed into a **quantum circuit**.
* A model containing **placeholders, classical or QML elements** cannot be represented as a circuit alone. In this case, it is transformed into a **quantum workflow** that preserves the higher-level structure and allows the corresponding elements to be resolved during workflow execution.

## Transformation process

The transformation of a model into an executable representation consists of several steps.

### 1. Model analysis

First, the model is analysed to identify its structural elements.

The transformation process identifies:

* nodes and their types
* groups and their hierarchy
* connections and edges
* classical tasks
* service tasks
* quantum tasks
* placeholders
* QML nodes
* attached metadata

This creates an intermediate representation that can be processed by the backend.

### 2. Group identification

Groups within the model are identified and their relationships are preserved.

Groups provide a way to structure complex models into meaningful sections. During transformation, these structures are analysed so that the resulting workflow retains the relevant semantic relationships of the original model.

### 3. Metadata attachment

Metadata associated with nodes, groups, and other model elements is attached to the corresponding elements of the intermediate representation.

This metadata can provide additional information required for execution, configuration, provenance, or later processing.

### 4. Merging

Related elements are then merged where required by the execution model.

This step transforms the graphical representation into a more compact execution-oriented representation while preserving the semantics of the original model.

### 5. Reassignment of edges

After elements have been transformed or merged, their connections need to be reassigned.

The original edges of the model are therefore mapped to the corresponding elements in the transformed representation. This ensures that the execution order and dependencies defined by the original model remain intact.

## 6. Task transformation

Different types of tasks are mapped to corresponding executable tasks.

### Classical elements

Classical elements are transformed into **service tasks**. They can represent interactions with external services or other computational resources required during workflow execution.

### Quantum elements

Quantum elements are transformed according to their contents and execution requirements.

A quantum task can ultimately become a **quantum circuit execution task**. The corresponding quantum operations are collected and transformed into a quantum circuit that can be submitted to a quantum backend.

If a **measurement** is present, it is explicitly represented as part of the quantum circuit execution. The measurement result can then be passed back into the surrounding workflow and used by subsequent classical or quantum tasks.


### 7. QRM creation

Once the transformation and task mapping have been completed, the backend creates the corresponding **QRM (QuantME Replacement Models)**.

The QRM contains the execution-ready replacement of the quantum model and contains the information required to execute and coordinate the resulting quantum and classical tasks.

The overall transformation can therefore be summarized as:

**Qonstruct Model → Analysis → Group Identification → Metadata Attachment → Merging → Edge Reassignment → Task Transformation → Quantum Circuit / Quantum Workflow → QRM Creation**
