## Overview

Qonstruct is a collaborative low-code modeling platform for designing and executing quantum applications. It provides a visual, node-based environment in which users can combine quantum and classical logic to model applications at different levels of abstraction.

The architecture consists of two main parts:

* **Qonstruct**, which provides the visual modeling environment and prepares models for execution.
* **Backend and execution services**, which enrich, transform, deploy, and execute the resulting models.

## Qonstruct

The Qonstruct modeler is the main entry point for creating quantum applications. It supports the modeling and execution phases of the application development process.

The modeler consists of several core components:

### Editor

The **Editor** provides the visual modeling environment. Users create applications by dragging modeling elements from the palette onto the canvas and connecting them to describe quantum and classical behavior.

### Validator

The **Validator** checks models while they are being created. It verifies structural and semantic constraints such as valid connections, compatible inputs and outputs, and other constraints defined by the modeling language.

Validation helps identify invalid models before they are sent to the backend.

### Transformer

The **Transformer** prepares a validated model for backend processing. It removes metadata that is specific to the modeling environment and produces the representation expected by the backend.

### Connector

The **Connector** communicates with external services used by Qonstruct. In particular, it sends models to the low-code backend and receives the resulting execution artifacts.

### Template Library

The **Template Library** provides reusable application and algorithm templates. Templates allow users to start from existing solutions instead of building every model from scratch.

## Modeling

Qonstruct provides modeling elements at different levels of abstraction. Users can combine higher-level application logic with lower-level quantum circuit elements.

The available elements are organized into the following categories:

* **Data Types**
* **Circuit-Level Nodes**
* **Boundary Nodes**
* **Operators**
* **Control Structure Nodes**
* **Custom Nodes**
* **ML Elements**

These elements can be combined to create quantum circuits, hybrid quantum-classical applications, and workflows.

See [Modeling Language](../modeling-language) for detailed information about the individual categories.

## Backend architecture

After a model has been validated, Qonstruct communicates with the **Low-Code Backend**.

The backend performs two main tasks:

1. **Model Enrichment** adds the implementations and information required to execute the modeled application.
2. **Model Transformation** converts the enriched model into an executable representation.

Internally, the backend represents the application as a directed graph containing quantum and classical nodes connected by data and control dependencies.

The backend supports different transformation targets depending on the modeled application.

### Quantum circuit execution

Models that can be represented as quantum circuits are transformed into **OpenQASM 3**.

The backend enriches the modeling constructs with their corresponding OpenQASM implementations and generates the resulting circuit representation.

### Workflows

Applications that contain classical logic, services, machine-learning components, or other workflow-level behavior are transformed into hybrid workflows.

The resulting workflow describes the interaction between quantum and classical components and can include:

* Quantum circuit execution
* Classical service tasks
* Machine-learning operations
* Control flow and data flow

The generated workflow can then be deployed and executed by the workflow infrastructure.

## Pattern-based modeling

Qonstruct integrates with the Pattern Atlas to support pattern-based quantum application development.

The Pattern Atlas provides:

* Quantum computing patterns
* Algorithm templates
* Pattern implementations

Qonstruct can retrieve algorithm templates and use pattern information to help users understand and construct quantum applications.

When an implementation for a modeling construct is available in the Pattern Atlas, the backend can use that implementation during model enrichment.

## Quantum backend selection

Before a quantum task is executed, the available quantum computers must be checked against the requirements of the task.

The **NISQ Analyzer** performs this selection and filters available quantum backends according to their capabilities.

For example, a model requiring mid-circuit measurements must only be executed on hardware supporting this capability.

The NISQ Analyzer uses information collected by **QProv**, which continuously gathers provenance and availability information about quantum devices.

The resulting selection is passed to **Qunicorn**, which provides a unified interface for executing quantum circuits across supported quantum backends.

## Machine learning integration

Qonstruct supports machine-learning elements through its integration with **QHAna**.

QHAna provides plugins for classical and quantum machine learning tasks such as data preparation and feature engineering.

During model enrichment, machine-learning elements can be resolved to QHAna plugins. In a generated workflow, these operations are represented as service tasks.

QHAna remains an independent service. Qonstruct communicates with the existing QHAna endpoint rather than embedding the QHAna implementation directly into the modeler or backend.

## Workflow execution

Applications containing both quantum and classical components are deployed as workflows.

The generated workflow can contain:

* Quantum execution tasks
* Classical service tasks
* QHAna machine-learning tasks
* Control-flow constructs
* Data-flow dependencies

The workflow engine coordinates these components during execution and provides runtime monitoring and logging.

The **OpenTOSCA ecosystem** is used to manage the deployment models describing the services and infrastructure required by the generated workflows.
